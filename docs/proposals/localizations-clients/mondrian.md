## 1. Summary and verdict

**READER and WRITER. Heavy: localizations are Mondrian's core purpose.** It displays and edits ROIs over still images. It reads them by scanning `Annotation.getAssociations()` for link names `bounding box`, `localization-line`, `localization-point`, `localization-polygon` (`javafx/roi/RoiTranslators.java:22-27`) and parsing `link_value` JSON as integer pixels (`domain/BoundingBox.java`, `domain/Points.java`). It writes them as associations: new ROIs are posted inside a new `Annotation` (`CreateVarsLocalizationCmd`), edits go through `AssociationService.update` (`UpdateLocalizationCmd`), ML predictions are bulk-created as `bounding box` associations (`MachineLearningResponse`, `MLUtils`). It embeds `image_reference_uuid` (and `comment`) in the JSON. The app's identity model equates localization UUID with association UUID, and one ROI == one Annotation == one observation. Mondrian does not read or write `generator`/`verifier`/`tags` except `generator` and `confidence` fields present on the `BoundingBox` POJO. It never subscribes to ZeroMQ. It does no export. Every localization code path breaks at cutover, so Mondrian is on the Phase 0 inventory as both reader and writer.

Dependencies: `org.mbari.vars:annosaurus-java-sdk:0.0.11` (`mondrian/build.gradle.kts:73`) supplies `Annotation`, `Association`, `Image`, and the HTTP client; `org.mbari.imgfx:imgfx:0.0.17` (`:72`) supplies the ROI views. Whether the SDK has localization support is outside this repo and must be checked.

## 3. Behavior and semantic changes to watch

- **Pixels to normalized, and Mondrian already has the dimensions.** The imgfx views are in image pixel space (`fromImageCoords` + `paneController.getAutoscale()`). Width/height are available from the loaded `javafx.scene.image.Image` (`AppPaneController.java:55`; `AnnotationPaneController.java:87-96` also lazily fills `Image.setWidth/Height` via `ImageIO`). Normalize on write and denormalize on read using the displayed image's size. Do not use sdk `Image.getWidth()` blindly: it is null until read (`AnnotationPaneController.java:89`). Mondrian is the one place with a guaranteed bitmap, so it must write correct normalized values.
- **Media assumption.** Mondrian draws on a framegrab. Normalized values are valid for the video only if the framegrab has the same FOV and aspect ratio. This app is the writer that creates that assumption, so cropped/letterboxed images must not be offered for localization.
- **Rounding.** Today `toInt` rounds to whole pixels (`RoiTranslator.java:38-40`). New values are doubles; do not round. Round trips (px -> norm -> px) must tolerate `EPS=1e-6`; clamp near-edge values by edge, not by origin/extent (proposal 6.2).
- **Out of frame.** Boxes can be dragged beyond the image. The server `CHECK` rejects `x+width>1`; clamp and set `truncated=true`, reject if no overlap.
- **Confidence scale 0-1 (D-15).** `BoundingBox.confidence` (`domain/BoundingBox.java:14`) fed from Megalodon `scores.get(0)` (`MachineLearningResponse1.java:39-40`). New writes must always be 0-1; a value above 1 hits the `CHECK` and, because bulk is per-batch, the whole batch fails. The migration (not Mondrian) rescales legacy 0-100 videos per video (any value above 1 makes the whole video 0-100). The owner confirmed uploads are per video (`vars-cli ml upload` writes 0-100, `ml upload-images` writes 0-1, one pipeline per video), so a video never mixes scales and the rule cannot corrupt data; no pre-migration check is needed for Mondrian. Mondrian must not divide stored values it reads back, since they are already 0-1.
- **`tags`/`training`.** Mondrian never reads or writes `tags`; but because it round-trips the whole link_value only via its own POJO (`BoundingBox` has no `tags`, `verifier`), an edit through Mondrian today strips `tags`, `verifier` and any extra key. New model avoids this only if the PUT preserves provenance (see #11): send back what was read, or use a PATCH-style SDK call.
- **One-per-type.** Mondrian creates a new Annotation per ROI (`CreateVarsLocalizationCmd.java:57-61`), so duplicates never arise from drawing. The collision case is "annotate existing" (i18n key `vip.annotate.existing` is defined at `main/resources/i18n.properties:48` but unused in code, so it is not implemented) and anywhere an observation selected from another tool already has a box: a second box of the same type would overwrite via upsert. UI must either block or warn.
- **409 on stale `last_updated_timestamp`.** Edits are drag-and-release (`AppController.java:350-359`), then fire-and-forget `UpdateLocalizationCmd`. With the new PUT, handle 409: refetch, show conflict, and do not push the stale value onto the undo stack (undo at `UpdateLocalizationCmd.java:57-86` also needs fresh timestamps, since the undo PUT itself changes `last_updated_timestamp`).
- **UUID identity.** imgfx `Localization.setUuid(association.getUuid())` (`VarsLocalization.java:112-113`), `SupportUtils.replaceIn`, `intersection`, and `AppController.java:213-270` all rely on the association UUID being the localization's id. Migrated rows reuse the association UUID (proposal 8.2), but new rows get server-generated UUIDs unless the client supplies one. The PUT is keyed by `(observation_uuid, type)` (7.2), so Mondrian can map the response back by that key; whether PUT accepts a client UUID is still unstated (open, below).
- **Bulk is per batch.** `POST /v1/localizations/bulk` and annotation bulk create (which now accepts `localizations`) reject the whole batch on one invalid item and write nothing (7.2). See #31.
- **Annotation create carries localizations.** `POST /v1/annotations` and `/bulk` accept `localizations` in each body, same validation as the localization PUT, same transaction; an invalid localization fails the request, so an annotation is never created with some localizations missing. `PUT /v1/annotations/{uuid}` does not carry them (proposed); edits use `PUT /v1/localizations/{observation_uuid}/{type}` (#18).
- **`part` and `difficult`.** Part (D-13) replaces the legacy association `to_concept`: the migration maps the literal `self` to NULL and copies anything else verbatim. Mondrian always wrote `self`, so its migrated boxes have NULL `part`; it must only preserve `part` on edit and never write `self`. `difficult` (D-16) is boolean, default false.
- **Orphaned image references.** The migration falls back to the video's dimensions (not quarantined), so migrated boxes whose image reference was missing are normalized by video size, which is exactly the media assumption above; Mondrian needs no handling.
- **`image_reference_uuid` dropped.** Used only as a stored hint (`BoundingBox`, `Points`, `AuxInfo`, translators); never read for logic. Removal is straightforward. The image-to-annotation lookup in `AppController.java:178-184` is by image reference on the annotation side, not from the JSON.
- **Comment.** The localization `comment` field maps to the new `comment` column; the dialog is `ifx.comment.dialog.*` (`i18n.properties:26-27`).
- **Marker/circle.** `Datums` supports `CircleData`, `DatumCircle` exists, but there is no circle translator and no `localization-circle` link name; only `point`. Not affected.
- **Masks.** Not supported by Mondrian; ignore or hide `mask` localizations returned in `Annotation.localizations`.

## 4. Dependencies and ordering

1. New `annosaurus-java-sdk` release exposing the `Localization` model, `Annotation.localizations` (and `AnnotationSC` snake-case), `localizations` on annotation create (single and bulk), PUT/DELETE/GET calls, and a typed 409. Mondrian cannot start until this exists (`build.gradle.kts:73`).
2. imgfx (`0.0.17`) is pixel-space; confirm no change needed (normalization is done in Mondrian's translators). If imgfx will offer normalized helpers, coordinate.
3. Ship Mondrian's release in parallel with Phase 2, ready before Phase 3 cutover. After cutover the old Mondrian shows no ROIs (association reads exclude them) and gets 400 on every create/edit, so there is no graceful fallback.
4. Megalodon (`services/pythia/OkHttpMegalodonService`) output units/confidence scale must be confirmed independently (#30).
5. Cutover window is TBD; it will be announced once all apps are aligned, so Mondrian's release date is set by that announcement, not by a `Sunset` date.

## 6. Risks and open questions

- **Biggest risk: hard cutover plus a full rewrite of the persistence bridge.** The association-keyed identity model (UUID, replaceIn, intersection, undo/redo) is threaded through ~12 files. Underestimating #12/#18 is the main schedule risk.
- Silent data loss on edit exists today (POJO drops unknown keys, incl. `verifier`, `tags`). Confirm the new DTO round-trips all provenance, `part` and `difficult` so Mondrian does not undo the proposal's benefits.
- Does the SDK `Annotation` serialize `localizations` on `create` (needs the SDK release, #1), and on `updateAll` (#26) will it clobber server state with a stale copy? (Server side: create accepts them; `PUT /v1/annotations/{uuid}` does not carry them, proposed.) Response shape for failing items is left to the implementation (#31).
- Resolved (2026-10-28), was open: `GET /v1/annotations/imagereference/{uuid}` (#27) survives and returns annotations including `localizations`; the owner confirmed it is the annotations endpoint, and that removing `image_reference_uuid` from localizations has no impact.
- Client-supplied localization UUID on PUT/POST (needed for imgfx identity, #12), or server-assigned and mapped back by `(observation, type)`?
- UI policy when an existing observation already has a localization of the chosen type (one-per-type).
- Which framegrabs lack the media assumption (crops/proxies)? Mondrian should refuse to annotate those.
- Does Megalodon emit 0-1 confidence (#30)? (Independent of legacy data scale.)
- Should Mondrian expose `part`, `difficult`, `training`, `truncated`, `verifier`/`verification_timestamp`? Not required for parity (round-trip only); out of scope unless product wants it.

### Resolved (from the proposal's section 13 and decisions)

- **Part has no home**: resolved, D-13. Nullable free-text `part varchar(128)`, no validation, replaces legacy `to_concept`. Mondrian only preserves it (#29). Decision (2026-10-28): the migration stores NULL for legacy `to_concept` = `self` (exact, case-sensitive) and copies other values verbatim; Mondrian wrote `self` itself, so migrated boxes have NULL `part`; clients must not write `self` into `part`.
- **Confidence scale**: resolved, D-15. Stored 0-1; migration picks the scale per video (any value above 1 makes the video 0-100, divided by 100). New writes are always 0-1 (#30). Rule kept (2026-10-28): uploads are per video (`ml upload` 0-100, `ml upload-images` 0-1, one pipeline per video), so a video does not mix scales and no mixed-scale corruption risk remains; no pre-migration check needed for Mondrian.
- **Bulk atomicity**: resolved. Transactional per batch, upsert by `(observation_uuid, type)`; clients wanting partial success split their own batches (#31). Applies to annotation bulk create too.
- **Annotation create carries localizations**: resolved (2026-10-28). `POST /v1/annotations` and `/bulk` accept `localizations`, validated as for the localization PUT, written in one transaction; invalid fails the request. Creation stays one atomic call (#16); `PUT /v1/annotations/{uuid}` does not carry them (proposed). The ML batch stays on annotation bulk create; the SDK still needs a release adding the field (#1, #23).
- **Orphaned image references**: resolved. Migration falls back to the video's dimensions.
- **`difficult`**: resolved, D-16. Boolean, default false, migrated rows false.
- **Query surface**: resolved, D-14. `/query` no longer returns localizations; new `localized_annotations` view and `/v1/localizations/query/*`. Not used by Mondrian; no work. 2026-10-28: the view has no image columns and `POST /v1/localizations/query/count` exists; still no work here.
- **Mask link name, second tag, `video_references` SELECT grant**: answered (none exist; `training` is the only tag; grant present). Cutover window: TBD.
