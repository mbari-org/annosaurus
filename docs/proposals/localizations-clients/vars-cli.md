## 1. How the app touches localizations today

**Verdict: BOTH reader and writer, bounding boxes only.** vars-cli has no code for points, lines, polygons or masks.

- **Writes.** It creates `bounding box` associations (pixel `x/y/width/height` JSON in `link_value`, with `generator`, `confidence`, and sometimes `image_reference_uuid`) inside new `Annotation`s. This happens in the `ml upload` path (`ToAnnotation`), the `ml upload-images` path (`PushImagesToVars`, with COCO input from `ml convert-ultralytics`), and the dead-looking `EventTrack.asAnnotation`. It also rewrites existing box associations in place in `anno standardize-bounding-box`.
- **Reads.** It parses `bounding box` associations off fetched annotations. Consumers: `boundingboxes draw-for-video` and the issue-56 frame capturer, which draw boxes on captured frames in pixels; `anno fetch-bounding-boxes-by-video`, which exports a pixel CSV; the IoU dedupe in `ml upload-images`; and the standalone script `src/universal/bin/anno_drop_localizations.sc`.
- **Not affected.** `ToLocalization`, `RawEventViewer` and `src/universal/bin/util_send_localizations_to_sharktopoda_test.*` send pixel boxes to Sharktopoda over vcr4j/UDP and never touch annosaurus. They stay in pixels.
- **No messaging.** There is no ZeroMQ or other messaging subscriber for annotations.
- **No hard-coded `localization-*` link names** (only `"bounding box"`).
- **Server-side filters.** Nothing uses link-name server-side filters for boxes. The `findByVideoReferenceAndLinkName*` calls in `services/AnnotationServiceOps.scala:309,319,336` only look for `identity-reference`.

## 3. Behavior and semantic changes to watch

- **Pixels to normalized, and where dimensions come from.** Writers have the dimensions in hand:
  - COCO input (`CocoImage.width/height`, `etc/coco/CocoDataset.scala:33-34`, populated from the image header at `apps/ml/UltralyticsToCoco.scala:130`).
  - `Media.getWidth/getHeight` for visual events (row 6). `Media` dimensions are nullable in vampire-squid, so add a hard failure instead of dividing by zero or null.
  - Readers that draw have the captured `BufferedImage`.
  - The only reader that needs a separate source is the CSV export (row 15), which needs media dims or a unit change.
- **Needless round trip in the Ultralytics path.** `UltralyticsToCoco.toAnnotation` (`apps/ml/UltralyticsToCoco.scala:255-262`) converts Ultralytics normalized YOLO boxes to rounded pixels (`round2`) for COCO, and the upload then divides them back. This is lossy only at 0.01 px, which is acceptable, but note the EXIF-rotation handling at `:120-132` that swaps width/height; normalization must use those same rotated dimensions (already carried in `CocoImage`).
- **Boxes crossing the frame edge.** COCO/YOLO boxes can extend slightly beyond the frame. The server rejects `x + width > 1 + 1e-6`. vars-cli must clamp and set `truncated = true` (per proposal section 6.2) for both uploaders; today there is no clamping anywhere.
- **Confidence scale (D-15).** Stored 0-1; the migration's per-video rule is kept and is safe for vars-cli because uploads are per video (owner-confirmed: `ml upload` writes 0-100 and `ml upload-images` writes 0-1, each as one pipeline per video, so a video does not mix scales). New writes must always send 0-1; vars-cli must not write 0-100 any more.
  - `.tracks`/visual events carry 0-100 (see `src/test/resources/visualevents/f000003.json`, e.g. `"confidence": 73`). `ToAnnotation` writes them raw today, so divide by 100 at the write boundary. The server `CHECK` rejects anything above 1, so a missed division fails loudly (and, per row 21, fails its whole batch).
  - COCO `score` and Ultralytics `conf` are already 0-1. `PushImagesToVars` writes them raw; keep that, do not divide. Existing 0-1 writers are not divided by the migration either (per-video rule, Resolved list).
  - CLI `--confidence` thresholds are in each source's own scale (visual-events default 20 per `src/docs/_docs/commands/sharktopoda.md:8`; `ml upload-images` filters 0-1 scores at `PushImagesToVars.scala:113`). Do not change the flag semantics; convert only at the write boundary. Note the inconsistency in the docs.
- **tags to training.** vars-cli never writes or reads `tags` (grep found none), so no mapping needed. `training` is the only tag (no second tag is planned). Optionally expose `--training` on the uploaders.
- **part and difficult.** vars-cli neither reads nor writes an organism part or a difficult flag today (row 22). It does write `VALUE_SELF` into the legacy `to_concept`; the migration turns that `'self'` into NULL `part`, so migrated boxes carry no part, and clients must not write `'self'` into `part`. Migrated rows get `difficult = false`.
- **Bulk is per-batch transactional.** One invalid item rejects the whole batch (default 50 in `newAnnotationsInBatches`) and nothing is written; the response names the failing item(s). Row 21.
- **One localization per (observation, type).** Both uploaders already create one observation per box, so they comply. The risk is `ml upload` with `--force`/re-runs against existing observations: `ToAnnotation` reuses `v.uuid` as `observationUuid` (`etc/yolo/VisualEventTransform.scala:60`), so a second run could now hit upsert (last-write-wins unless `last_updated_timestamp` is sent) instead of creating a duplicate box. Confirm the intended behavior.
- **409 handling.** Nothing in vars-cli does optimistic concurrency. `anno standardize-bounding-box` (to be deleted) was the only in-place editor. If an upsert flow is added, send `last_updated_timestamp` only when updating a row that was previously read, and treat 409 as "skip and report", not retry.
- **image_reference_uuid dropped.**
  - Removed from the box model (rows 2, 8, 9, 10).
  - Still needed as an *image lookup key* for `ml upload-images` (`ImageRef.imageReferenceUuid`, `PushImagesToVars.scala:121`; COCO `vars_image_reference_uuid`). That is unrelated to the box and stays. The by-uuid image reference lookup (`lookupImageByUuid`, `services/AnnotationServiceOps.scala:218`) is unaffected by the proposal.
  - `isIouDuplicate`'s cross-image filter goes away.
  - Consequence: a box drawn on image A is now indistinguishable from one drawn on image B of the same moment; the same-aspect-ratio assumption becomes load-bearing for `Dedupe.Iou`.
- **Associations no longer return boxes.** `getAssociations` on fetched annotations will not contain boxes; any code left on the association path silently sees "no boxes" instead of failing (draw commands print `No bounding boxes found ... skipping capture`, `CaptureAndDrawAnnotations.scala:76`). Make sure the cutover test covers this.
- **Writes of box associations get 400.** Any leftover `Association("bounding box", ...)` construction (rows 3, 6, 7, 9) will fail at runtime, not compile time.

## 4. Dependencies and ordering

1. Annosaurus ships the table, endpoints and `Annotation.localizations`.
2. `annosaurus-java-sdk` release with the `Localization` model plus the new endpoint methods and `Annotation.localizations` serialization. vars-cli cannot start until this exists (row 1). The SDK must serialize `localizations` in `POST /v1/annotations` and `/bulk` bodies (the server accepts them; resolved), so both uploaders (`PushImagesToVars.uploadBatches` at `:365-380`, and `VisualEventSink` at `:81`) keep creating observation + box in one batched call and their batching and `resumeHint` (`:383-387`) logic stay structurally unchanged. `PUT /v1/annotations/{uuid}` does not carry localizations (proposed).
   The SDK must also cover `part`, `difficult`, `POST /v1/localizations/bulk`, the optional `last_updated_timestamp` on PUT (409), and, only if row 23 is wanted, `/v1/localizations/query/{columns,run,download,count}`.
3. vars-cli release, in step with Phase 3 cutover of annosaurus (proposal section 12). The cutover date is TBD; it will be announced once all apps are aligned. There is no compatibility window: the old vars-cli gets 400 on every box write and silently reads zero boxes.
4. Only the CSV export and drawing commands are read-only; they could ship earlier against a server that has both representations (between Phase 2 and Phase 3), but the proposal says nothing returns boxes as associations after cutover, so a combined release is simpler.

## 6. Risks and open questions for the maintainers

Open:

1. **SDK release (biggest risk).** Everything is blocked on `annosaurus-java-sdk` shipping the `Localization` model, `Annotation.localizations` (including on create bodies) and the new endpoint calls (row 1).
2. **Silent wrongness at read.** Readers that miss the cutover show "no boxes" rather than erroring (`CaptureAndDrawAnnotations.scala:76` only warns). Add a startup/version check or an explicit error when `getLocalizations` is absent from the response.
3. **Media dimensions may be missing.** `Media.getWidth/getHeight` is nullable; normalization of visual-events uploads needs a policy (fail the whole video, or skip boxes). With per-batch transactions, a skipped-vs-failed choice should be made before sending.
4. **Reruns now upsert.** See section 3 (one per type). Decide whether `ml upload --force` should replace, skip, or fail, and whether to send `last_updated_timestamp`.
5. **CSV export units.** Pixels (needs media dims) or normalized? Downstream consumers of `fetch-bounding-boxes-by-video` output are unknown.
6. **Frame-grab dimensions.** The draw commands assume the grabbed frame is the full, uncropped, un-letterboxed field of view. Verify for the Sharktopoda/Beholder/ffmpeg grabbers.
7. **Dead code.** `EventTrack.asAnnotation` and `AnnotationOps.boundingBoxAssociations` have no callers in this repo. Confirm before deleting, in case an out-of-repo script depends on them.
8. **Partial-success policy for bulk.** Whether vars-cli should auto-split a rejected batch (row 21) or just report and stop.

Resolved (proposal decisions):

- **Where does `part` go?** The `part` column (D-13, free text, no validation). vars-cli currently has no part handling; it must just not copy `"self"` (row 3).
- **`/query` for boxes.** No longer returns localizations; use `localized_annotations` via `/v1/localizations/query/*` (D-14, row 23). `annotations` view does not expose localizations; vars-gridview is its only consumer.
- **Confidence scale.** Stored 0-1; migration resolves legacy scale per video by hard rule (> 1 anywhere means whole video 0-100, divided by 100); new writes always 0-1 (D-15). Replaces the earlier "migration divides everything by 100" worry.
- **Mixed confidence scales within one video.** Resolved: uploads are per video (owner-confirmed; `ml upload` writes 0-100, `ml upload-images` writes 0-1, one pipeline per video), so the per-video rule is safe and no pre-migration check is needed for vars-cli. New writes must still send 0-1.
- **Does annotation create carry `localizations`?** Yes: `POST /v1/annotations` and `/bulk` accept them, validated like the PUT, in the same transaction; an invalid one fails the request. Uploaders keep single-call atomicity and need no PUT-per-observation step (rows 6, 9). `PUT /v1/annotations/{uuid}` does not carry them (proposed).
- **`part` for legacy `'self'`.** Migration stores NULL for `'self'`; any other `to_concept` is copied verbatim. vars-cli must not write `'self'` (row 3).
- **Image columns and count endpoint.** `localized_annotations` has no `image_reference_uuid`, `image_url` or `image_format`; a client picks an image from `imaged_moment_uuid` itself. `POST /v1/localizations/query/count` lives under `/v1/localizations/query/` (row 23).
- **Image reference by uuid.** `GET` of an image reference by uuid is unaffected by the proposal (the doc's `lookupImageByUuid`, `AnnotationServiceOps.scala:218`). The annotations-by-image-reference endpoint (`GET /v1/annotations/imagereference/{uuid}`, row 11) is a different endpoint, and is confirmed (2026-10-28) to survive and return `localizations`.
