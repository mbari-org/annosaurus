## 1. Summary — READER and WRITER (both, heavily)

vars-annotation reads and writes localizations exclusively as `associations` via the `annosaurus-java-sdk` (0.1.0, which has no localization support; `Association.NAME_LOCALIZATION = "bounding box"` and a pixel-int `BoundingBox` bean live in the SDK). It uses all four legacy link names (`bounding box`, `localization-point`, `localization-line`, `localization-polygon`; no mask). Three paths:

1. **Sharktopoda video localizations** (`ui/mediaplayers/sharktopoda2`): bounding boxes only. Outgoing: scans `annotation.getAssociations()` for `bounding box`, parses the pixel JSON, and sends `Localization` objects (pixels) over ZeroMQ to Sharktopoda. Incoming (add/update/remove from Sharktopoda): builds the pixel JSON and creates/updates/deletes the association. The association UUID is reused as the Sharktopoda localization UUID and is the matching key.
2. **imgfx image-pane editor** (`ui/javafx/imgfx`): draws all four types on framegrabs. Reads them from associations (pixels to `RectangleView.fromImageCoords`), writes them back as associations with `image_reference_uuid` and `comment`.
3. **ML stage** (`ui/javafx/mlstage`) writes a `bounding box` association (pixels, generator "VARS Annotation") per accepted ML detection, in bulk-created annotations. Also `ui/javafx/imagestage/ImageStage2` reads boxes for display, and `CopyAnnotationsCmd` strips them on copy.

The app does not subscribe to annosaurus ZeroMQ notifications (the `localization.*` keys in `reference.conf:71-83` and `AppConfig.java:155-165` are the Sharktopoda channel, unaffected). It does no YOLO/VOC/COCO export. It does not read the `annotations` view.

## 3. Behavior and semantic changes to watch

- **Pixels to normalized (the central risk).** Every read must scale by a width/height; every write must divide. Sources of dimensions:
  - Sharktopoda path: `toolBox.getData().getMedia()` (`Media.getWidth()/getHeight()`, vampire-squid); `LocalizedAnnotation.java:90,107-108` already uses media width/height. Needs a null-safe policy when a video has no dimensions (nullable in vampire-squid).
  - imgfx and ImageStage2: the displayed `javafx.scene.image.Image` (`IFXPaneController.java:82`, `IFXVarsPaneController.java:234`), i.e. the framegrab pixel size, not the video size.
  - ML stage: dimensions of the framegrab sent to Pythia (`imageData`).
  This relies on the proposal's media-assumption (section 6.2): same FOV/aspect for image and video. The app already warns about non-1 aspect ratio in dead code (`BoundingBoxDecorator.java:69`), so this has bitten before.
- **Rounding.** Current writes truncate to `int` via `Roi.toInt` (`Roi.java:28`) and `MLUtil.doubleToInt`. Normalized doubles remove that quantization; use the edge-based snapping from the companion doc (clamp edges, derive width/height; set `truncated` when clamping) rather than clamping x and width separately.
- **One per (observation, type) vs. multiple boxes per annotation.** The app currently allows several `bounding box` associations on one annotation and designs around it (`IncomingController.java:149-152` comment; `test/.../LocalizationSelectionEchoTest.java:65` "annotation with TWO bounding boxes"). That model is gone. Sharktopoda "add localization" on an annotation that already has a box, imgfx `localizeExistingAnnotation` (`AnnotationBuilder.java:51-58`) and the selection echo logic (`OutgoingController.java:104-108`) all need a rule (second box = new annotation/observation).
- **UUID identity.** Today localization UUID == association UUID (`VarsLocalization.java:106`, `IncomingController.java:87-94`, `LocalizedAnnotation.java:198`). The new row has its own `uuid`; upsert is keyed by `(observation_uuid, type)`. The "send Add, create, send Remove, resend" workaround may simplify or need re-thinking.
- **Provenance preserved on round trip.** The SDK `BoundingBox` has no `confidence`, `tags`, `observer`; today any edit via `UpdateAssociationCmd` rewrites the JSON from the Sharktopoda box with generator "VARS Annotation" (`LocalizedAnnotation.java:191`), silently discarding other tools' `generator`/`verifier`/`confidence`/`tags`. This is the tug-of-war in the proposal. With the new model, updates must PUT the full row (merge edited geometry into the fetched row), or editing a ML-generated, verified box will clobber its provenance. Decide who sets `verifier`/`verification_timestamp` when a human edits or accepts a box.
- **Confidence scale (D-5, D-15).** The app never reads or writes `confidence` today (parsed from ML in `MachineLearningLocalization` then dropped), so it is not a legacy 0-100 writer and its migrated rows (none) are unaffected. Stored scale is 0-1 and the `CHECK` rejects values above 1. New writes must always send 0-1: normalize whatever Pythia returns before sending (open: what Pythia returns, Q8). Existing 0-1 writers are not divided by the migration, so nothing here needs a compensating change.
- **tags to `training`.** The app does not read or write `tags` (the SDK bean lacks it; `test/.../BoundingBoxTest.java:17` JSON has `observer`, `strength`, `project`, which the bean ignores). `training` is the only tag (no second tag is planned). Nothing to migrate in-app; just expose `training` if a UI is wanted, and preserve it on PUT merge.
- **`part` and `difficult` (D-13, D-16).** The app only ever wrote `to_concept = "self"` and never reads it, so `part` needs no migration work here (migrated boxes carry NULL, not `self`); this app wrote `self` itself, so its change is to send or omit null instead; keep it null on new rows and preserve it on edits (#25). `difficult` is new, default false, preserve on edits (#26). Omitting either from a PUT body that replaces the row risks resetting another tool's value, so PUT must carry the full fetched row.
- **Bulk is all-or-nothing per batch.** One invalid localization rejects its whole request with nothing written, on `POST /v1/localizations/bulk` and on annotation create and bulk create (#24). The ML stage today fires one bulk create for every accepted detection; one bad box would lose the lot, so validate client-side (edge clamping, `truncated`, 0-1 confidence) and chunk.
- **Orphaned image references.** Not an app concern: the migration falls back to the video's dimensions (section 11.2 of the proposal), which is right for boxes drawn on framegrabs only if the media assumption holds (already noted above).
- **409 handling.** Updates from Sharktopoda drags arrive rapidly and from a stale local snapshot (`AnnotationSnapshots.snapshot`, `IncomingController.java:164`). If `last_updated_timestamp` is sent, 409 will occur; the app needs a refetch-and-retry or last-write-wins policy. Omitting the timestamp keeps today's behavior.
- **`image_reference_uuid` dropped.** Written by `RoiBoundingBox.java:68`, `Points.java`, and `AnnotationBuilder` (`:58,67`), read by dead `BoundingBoxDecorator`. A box drawn on a framegrab is no longer tied to that image; selecting an image now finds localizations by imaged moment (`LookupUtil.getAnnotationsForImage`, `:38-51` already does this). Cross-moment annotation pulls (old VARS Localize case) cannot be represented.
- **Association guard.** After cutover, any code path that submits a localization link name to association endpoints gets 400, and association reads no longer contain them. Hard-coded `"bounding box"` / `"localization-*"` strings must all be gone (rows 2, 9-11, 15, 16, 17, 20). `RectLabelController`'s dead code still has them; remove to avoid accidental revival.
- **Table display.** Annotation table cells will stop showing localization JSON (#18).

## 6. Risks and open questions

Risks
- The Sharktopoda path is the highest risk: live, high-frequency, UUID-matching, mixed threads, pixel/normalized conversion done on the event bus; a wrong media dimension misplaces every box without an error.
- Silent provenance loss persists if updates are built from the bare Sharktopoda/imgfx box instead of merging into the fetched row.
- Users running an old build after cutover get 400s and invisible boxes; no fallback.
- Undo/redo of localization commands (restore the prior row, handle 409 on undo) is new surface.
- Whole-repo reliance on `Association` as the carrier (events, VarsLocalization, commands) makes the refactor wider than the file count suggests.

Resolved by the revised proposal
- Where `part` lives: nullable free-text `part varchar(128)`, no validation (D-13). This app writes only "self" today and never reads it (#25).
- `difficult`: new boolean column, default false (D-16). Preserve it (#26).
- Confidence: stored 0-1; the migration resolves legacy scale per video (any value > 1 in a video => whole video 0-100, divided by 100). Rule kept: uploads are per video (vars-cli `ml upload` writes 0-100, `ml upload-images` writes 0-1, one pipeline per video), so a video does not mix scales and no mixed-scale corruption risk remains (D-5, D-15). All new writes send 0-1. Pythia's own scale is still open (Q8).
- Annotation create carries `localizations` (formerly Q3): `POST /v1/annotations` and `/bulk` accept them, same validation as PUT, same transaction, an invalid one fails the request; `PUT /v1/annotations/{uuid}` does not carry them. Creation stays one atomic call; edits use `PUT /v1/localizations/{observation_uuid}/{type}` (#3, #13, #16, #24).
- `self` stored as NULL (D-13): migrated boxes have NULL `part`; clients must not write `self` (#25).
- Bulk semantics: per-batch transactional, client splits for partial success (#24). Upsert by `(observation_uuid, type)`; PUT may send `last_updated_timestamp` for 409.
- Orphaned image references fall back to video dimensions; no mask link name exists; only `training` tag; cutover window TBD (announced when all apps are aligned); annosaurus has SELECT on `M3_VIDEO_ASSETS.dbo.video_references`. None changes this app.
- Query surface: `/query` no longer returns localizations; new `localized_annotations` view and `localizations/query/*` endpoints serve vars-gridview only. No work here.

Open questions for maintainers (still open)
1. Q1: Which model for two boxes on one observation: auto-create a new annotation, prompt, or block? (Affects Sharktopoda add and imgfx "localize existing annotation".)
2. Q2: Will vars-annotation set `generator` = "VARS Annotation", `observer`, `observation_timestamp` on write, and `verifier`/`verification_timestamp` when a human edits an ML box? (The full-column DTO question is settled.)
4. Q4: Does Sharktopoda still need pixel coordinates (so this app converts using vampire-squid `Media` width/height), and what should happen when media has null width/height?
5. Q5: Should the app send `last_updated_timestamp` (409 on conflict) or stay last-write-wins for Sharktopoda drags?
