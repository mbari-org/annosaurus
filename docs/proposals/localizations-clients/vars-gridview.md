## 1. How the app touches localizations today

**Verdict: READER and WRITER, and localizations are the whole product.** VARS GridView ("reviewing and correcting VARS localizations in bulk", `README.md:3`) loads only `bounding box` associations through the Annosaurus query endpoint (`/query/...` TSV, `link_name = 'bounding box'`; after the change this moves to `/v1/localizations/query/*` over the new `localized_annotations` view, D-14, which has no image columns), parses the pixel JSON in `link_value`, and shows each box as an ROI tile cropped from the image (Skimmer) or video frame (Beholder). Users then edit through the association endpoints: change the box geometry (`link_value` rewritten via `PUT /associations/{uuid}`), change the "part" (`to_concept`), verify/unverify (`verifier` key), mark/unmark training (`tags: ["training"]`), change the observation concept, and delete the association or the whole observation. It also filters and sorts on JSON keys (`verifier`, `generator`, `confidence`, `image_reference_uuid`), and pushes boxes to Sharktopoda with pixel math. Only bounding boxes are handled; points, lines, polygons and masks are ignored. There is no ZeroMQ subscriber and no use of `Annotation`/`/annotations` for reading. The dependency on the legacy shape is total: when the cutover lands, `/query` returns no localizations and every save returns 400, so it must be released before cutover (proposal §12, Phase 3; date TBD, announced once all apps are aligned). GridView is the only consumer of the localization query surface (§13 Q5, Q13).

## 3. Semantic changes to watch

- **Pixels to normalized.** Everything downstream of the model is pixel-based: cropping (#12), the ROI editor (#13, #14), sorting (#11), Sharktopoda export (#17). The cleanest design is to convert once at the model boundary (normalized in the model, pixel properties derived from known source dimensions), so the UI code keeps working in pixels.
- **Dimensions are required for display and cropping.** Annosaurus stores none. Sources available in this app: `video_width`/`video_height` already fetched for every row (`controllers/query_controller.py:138-139`, stored in `localization_store.py:94-103`), the decoded image shape after fetching (`rect_widget.py:155`), and the proxy video reference width/height (`roi_loader.py:349-350`). For still images, `image_reference` dimensions (`width_pixels`/`height_pixels` in the schema) are not currently requested by the query and are not listed among the view's columns (§7.3), so image-dimension lookup is the client's job via `imaged_moment_uuid`. The existing assumption (box drawn on a framegrab shown on a video) is exactly the media assumption of proposal §6.2.
- **Saving needs dimensions too.** `get_box()` returns int pixels; PUT needs `x/image_width` etc. If the image dimensions are unknown at save time, the save must be refused rather than guess.
- **Edge clipping.** Dragging a handle beyond the frame is limited by `max_bounds` today. If a box ever reaches the frame edge, set `truncated=true` and snap by edges per §6.2.
- **Confidence scale (D-15).** Stored 0-1. The migration picks the scale per video (any legacy value above 1 means the whole video was 0-100 and is divided by 100; otherwise as is). This is safe because uploads are per video (`ml upload` writes 0-100, `ml upload-images` writes 0-1, one pipeline per video), so a video does not mix scales. GridView never converts on read. It only reads/sorts a value already in 0-1. GridView does not currently write confidence (it round-trips it in the JSON), but any write must send 0-1; send back the value read unchanged and never rescale. A value above 1 now fails the CHECK. Only `ConfidenceSort` and the info tree consume it; no UI formatting was found.
- **Part (D-13).** `part` replaces `to_concept` as a nullable free-text `varchar(128)` on the localization (#22). The part is no longer merged on an association; it travels in the whole-row PUT. The migration stores NULL for the legacy literal `"self"` (exact, case-sensitive) and copies any other `to_concept` verbatim. Treat NULL as no part and never write `"self"` (#22).
- **`difficult` (D-16).** New boolean, default false, false for all migrated rows. GridView must round-trip it (#23).
- **tags to training.** `mark_for_training` appends to a `tags` list (`association.py:355-370`). Becomes `training = true`. Other tag values are dropped by the migration (D-10). `hide_training`/`hide_nontraining` filters (`ui/mosaic/mosaic_view.py:154-158`) keep working through `is_training`.
- **One per (observation, type).** GridView treats a box as its own association row and can show several boxes per observation (`association_groups`, `roi_loader.py:258-275`). After migration there is at most one box per observation. The "delete only the box vs also the dangling observation" prompt (`annotation_action_coordinator.py:130-145`) still applies; the multi-box-per-observation display path becomes dead.
- **409 handling.** Today saves are last-write-wins partial merges. Under the new PUT, include `last_updated_timestamp` from load time. On 409, GridView needs a UX: reload the row, or tell the user and offer to overwrite. Saves occur on selection change and at shutdown (`rect_interaction_coordinator.py:102-155`, `shutdown_save_coordinator.py:55-135`), so a 409 must not block closing the app. Also refresh the held timestamp from each successful PUT response or later saves of the same box will 409 against themselves.
- **Whole-row PUT.** Verify, training, geometry and part are now one PUT of the full localization. Only the concept (observation PUT) remains a separate call, so partial-failure ordering in `AnnotationService.push_changes` (47-86) still matters, though there is one fewer call.
- **image_reference_uuid dropped.** It currently selects the image tile versus video-frame source (`localization_store.py:157`, `roi_loader.py:306`) and appears in sorting and the info pane. After the change the view exposes `imaged_moment_uuid` and GridView resolves image references itself (§13 Q11; the view has no image columns at all, neither `image_reference_uuid` nor `image_url`/`image_format`; an imaged moment can have several images), so it needs its own lookup and rule per imaged moment, criteria TBD, using existing image-reference endpoints (#26). `GET` of an image reference by uuid (`roi_loader.py:427`) is unaffected by the proposal. A possible rule: prefer an image reference if the moment has one, else the video frame). Orphaned legacy references migrate with the video's dimensions (§8.2, §11.2), so such boxes appear as video-frame boxes. Note that for historic cross-moment cases (§11.1) that rule changes what is displayed.
- **Observer/generator behavior.** `CHANGELOG.md:310-313` records deliberate behavior: keep `observer` original and do not update `generator`. Preserve that when writing: send existing `generator`/`observer` back unchanged and set only `verifier` (and `verification_timestamp`).

## 4. Dependencies and ordering

1. Annosaurus ships the table, `/v1/localizations/*` endpoints, the `localized_annotations` view and `/v1/localizations/query/{columns,run,download,count}` (blocks #2, #3, #10, #21). Annotation create now accepts `localizations` (atomic, same rules as the PUT); GridView creates no annotations, so this is not needed. `POST /v1/localizations/query/count` is part of the same delivery.
2. Migration routine run and rejects reviewed (Phase 2). Orphaned image references now migrate on the video's dimensions rather than being rejected; remaining rejects (duplicate type, malformed data, unresolved dimensions) are invisible in GridView afterward.
3. GridView has no shared Annosaurus client library: it carries its own `AnnosaurusClient` (`lib/m3/clients.py:193`). A new annosaurus-java-sdk / client release is needed by other apps, but GridView needs no external bump unless a common Python client is wanted.
4. GridView release must be ready before Phase 3 cutover (date TBD, announced once all apps are aligned); there is no compatibility window and the old build gets no data and 400s on writes. Cannot be dual-mode against the pre-migration server in a practical way (shapes differ), so either ship a flag or accept a hard version coupling with the server.

## 6. Resolved decisions and open questions

**Resolved by the revised proposal**

1. **Query endpoint (was the biggest gap).** D-14: `/query` no longer returns localizations. GridView moves to `localized_annotations` via `GET /v1/localizations/query/columns`, `POST .../run`, `POST .../download` (same request shape). Verifier, generator, confidence, training, truncated, part, `localization_type` are real columns; no `LIKE` on JSON. `concepts` matches the observation concept only. The `annotations` view does not expose localizations, and GridView is the only consumer (§13 Q5, Q13).
2. **Part.** D-13: nullable free-text `part varchar(128)` replaces `to_concept`; no validation (Q10). The migration stores NULL for `"self"` (exact match) and copies other values verbatim, so migrated boxes never carry `part='self'`. GridView must send null, not `"self"` (#22).
3. **Confidence.** D-15: stored 0-1; migration decides the legacy scale per video; new writes always 0-1; existing 0-1 writers are not divided. A mixed-scale video cannot occur: uploads are per video (`ml upload` 0-100, `ml upload-images` 0-1, one pipeline per video), confirmed by the owner. No pre-migration check is needed for this app.
4. **`difficult`.** D-16: boolean, default false (#23).
5. **Orphaned image references.** Migration falls back to the video's dimensions (Q3, §11.2).
6. **Bulk.** `/bulk` is transactional per batch, upsert by (observation_uuid, type); GridView does not use it (#24).
7. **Image vs video source.** The view exposes `imaged_moment_uuid`; clients resolve image references (Q11). The rule stays in GridView (section 3, #26).
8. **Mask link name, second tag, `M3_VIDEO_ASSETS` SELECT:** no existing mask link name, `training` is the only tag, annosaurus user has SELECT (Q1, Q7, Q9). Not GridView work. Cutover window: TBD (Q2).
9. **Image columns in the view (was Open Q1).** The view has no `image_reference_uuid`, `image_url` or `image_format`. GridView chooses an image itself from `imaged_moment_uuid` via existing image-reference endpoints; selection criteria are TBD (#2, #26).
10. **Count endpoint (was Open Q2).** `POST /v1/localizations/query/count` takes the same `QueryRequest` and returns the matching row count, for paging (#21).
11. **Annotation create with localizations.** `POST /v1/annotations` and `/bulk` accept `localizations`, validated like the PUT, same transaction, an invalid one fails the request; `PUT /v1/annotations/{uuid}` does not carry them. Not applicable to GridView (it creates no annotations); edits stay on `PUT /v1/localizations/{observation_uuid}/bounding_box`. Batching in #24 is unchanged.
12. **GET image reference by uuid.** Unaffected by the proposal; GridView uses it at `services/roi_loader.py:427`. (`GET /v1/annotations/imagereference/{uuid}` is a different endpoint; GridView does not use it.)

**Still open for this app**

1. **Dimensions for still images.** Skimmer crop takes pixels; the proposal stores no image size. Does the client fetch `width_pixels/height_pixels` from the image reference, or does Skimmer get a normalized crop?
2. **409 UX.** Reload, overwrite, or discard? Saves happen implicitly on selection change and at exit.
